# OOXML 차트 글줄의 하단 앵커와 범례 가용 프레임

## 원 해결과 독립 근거

원 이슈 #6624 → 기여 #6626 → 실제 통합 #6645의
`b1091864dffee8f8041e5b235d9ab9491ea41c04`를 현재 base/head와 대조했다.
제목14pt·축/범례10pt, 저장 font family와 실제 editable data 소비는 유지한다.
#8064의 legacy WMF/EMF 차트 개선을 이 OOXML 편집 가능 차트의 검증으로 대신하지 않는다.
이전 PR의 IoU·다른 fidelity 지표를 현 raw90% 통과로 바꾸어 보고하지 않는다.

원 실측 주석은 제목의 잉크 하단35.5px를 `baseline`으로 부르고 SVG의 alphabetic y로
넘긴다. 카테고리 라벨도 잉크 하단239.5px를 같은 방식으로 사용한다.621의 실제 HCRDotum
프로그램은 hhea1000em에 descent230이다. Native058 제목 잉크175..191와 독립 Print의
170..187 차이는 줄 하단을 alphabetic 기준선으로 사용한 것과 대응한다. 고정4px 이동이
아니라 SVG의 표준 text-after-edge로 실제 선택한 글꼴의 descent를 소비해야 한다.
usvg의 실제 alignment baseline 경로와 브라우저 SVG 모두 글꼴 기준선을 소비한다.

현재 우측 범례는 plot_y/plot_h 가운데를 사용한다. 그러나 독립 Print의 기본·반 크기·
세로 두 배 프레임은 제목 줄 하단부터 프레임 바닥 사이에 범례를 가운데 놓는다.640에서
제목14pt를 명시한 입력과 상속한 입력이 같은 결과였다. 반 크기 프레임의 독립 가운데
233.763px와 가운데 스와치233.5px, 세로 두 배의421.079px와421px가 대응한다.
기본 프레임도 예측295.4px와 실제 가운데295.5px가 대응한다. 문서 ID·프레임 고정 크기·
눈대중 이동 상수로 조건을 만들지 않는다.

## 실제 소비 경로와 적용 경계

`title_font_px` → 제목 아래끝 앵커/plot 예약 → SVG 제목과 하단 축 라벨 → Native usvg 및
fresh 브라우저 SVG의 실제 글꼴 기준선으로 연결한다. plot 예약의 기존 아래끝 기준은
그대로 두고 표시 기준선만 올바르게 구분한다. 우측 범례는 별도의 가용 프레임을 계산하여
`render_legend_right`에 전달한다. 하단 범례·실제 시리즈 데이터·축 범위·선폭은 건드리지 않는다.
제목 없는 차트는 제목 예약이0이며 전체 프레임에서 우측 범례를 가운데 놓는다.

## 검증 계획

Native 한 빌드에서 두 실제 차트 입력의 원본 독립 Print, 제목 크기·상속·프레임 반/두 배
대조를 먼저 실행한다. 같은 소스의 최적화 fresh에서도 확인한다. 전체 쪽수·전쪽 raw90%와
확대 review/overlay를 모두 확인한 뒤에만 관련 렌더링 회귀를 추가·변경한다. 이미 완료한
표 입력과 #8064 보존 sweep은 동결 producer058/026의 결과로 구분하며 새 소스의 최종
검증을 대신하지 않는다.

## 아래 여백 보정의 실제 원 PR

`git blame`과 commit→PR API 648에서 프레임 높이 `h/250`을 곱한 변경은 통합 #7437
merge `8baae33464bce7e92cbbd07e715397dca141f836`으로 추적했다. 원 기여 PR #7406은
KoPub 라틴 폭 수정이고, 차트 변경은 #7437의 메인터너 보정이다. 그 본문·커밋·실제 diff를
649~650에 보존했으며 #7406을 일반 이슈로 오인하지 않는다. 당시의 비최적화 fresh·옛
실루엣 수치·원본과 다른 색상 키 차이 기록을 현 raw 통과 근거로 대신하지 않는다.

실제 분리 입력 `samples/issue7406/7406_OLE__CHART.hwp`와 `.hwpx`를 저장 제품에 맞는
공식 한컴 2024 `13.0.0.3901`·PrintMethod 0·1-up으로 다시 출력했다. HWP는
`scripts_disabled`, HWPX는 `none`을 기록한다. 첫 client 검사에서 HWP도 `none`이라고
가정한 자체 assertion이 실패했지만 서버의 기존 성공 job을 다시 조회·다운로드했으며
재제출하지 않았다. 이를 엔진 변환 실패나 원본 변경으로 보고하지 않는다.

두 입력의 Native059 raw는 각각 93.17993%다. 654의 실제 review/overlay에서 표제·축·
범례와 값 레이블을 대조했다. 큰 프레임에서 여백을 무조건 원복하는 대신, 이 정상 대조의
플롯과 아래 범례 예약을 함께 유지하는 공통 원인을 확인한다. 28쌍 차트 코퍼스의 과거
파일명 `-2020.pdf`와 실제 Creator 2022 표기는 구별한다. 새 643의 버전별 공식 Print로
현재 source와 fixed base의 영향을 확인한다. 23개 선행 Native만으로 전체 56개를 보증하지 않는다.

별도로 Native058의 #8064 보존 실행 615는 179조건·2,082쪽을 전부 완료했고 0.1pp 이상
하락 0쪽이다. fresh026의 전체 실행 632는 계속 중이다. 이 결과는 059 변경 이후의 시각
증거로 바꾸어 쓰지 않는다.

실행 로그는 ignored output의 `logs/native059-charts-6-645.log`,
`logs/native059-focused-645.log`, `logs/mcp-chart-pr7437-651-attempt02.log`,
`logs/mcp-chart-corpus-643.log`, `logs/mcp-chart-layout-controls-653.log`에 있다.

## 공통 축·글줄 프레임의 추가 독립 근거

#7930 병합 `2e3b4f880b` 위로 120개 패치를 그대로 리베이스한 후보는 `311a342dab`이다.
새 devel과 후보에서 Qt 25개·클립보드 Rust 19개 및 실제 Native 창/ABI 경로가 모두 통과했다.
이 기능 보존 결과를 기존 차트의 새 head 시각 검증으로 바꾸어 쓰지는 않는다.

676의 값 3·4·6·12, 글자 8·12pt, 기본/두 배 높이 12개와 678의 값 0.2·1·20
여섯 입력을 같은 원본에서 생성했다. 두 OOXML 복사본과 chart/OLE의 크기를 함께 바꿨고
각각의 원문을 공식 2020 PrintMethod 0·1-up으로 출력했다. 원본 그대로의 통과로 세지 않는다.
677/679의 격자 위치는 가용 축 길이를 라벨 두 줄 높이로 나눈 예산(원 데이터 최대 열 칸),
그 예산보다 큰 1·2·5 계열 간격, 데이터 범위 10% 여유로 설명된다. 고정 눈금 수나 정수
최솟간격 가정은 배율 대조와 맞지 않아 채택하지 않는다.

682의 제목 8/20pt·제목 없음·하단/줄바꿈 범례·음수 기본/두 배 높이도 독립 Print로
추가했다. 687~689에서 범주 글자의 아래끝이 기본 프레임 여백에 고정되고, 음수에서는
범주 축이 0에 놓여 최하단 값 라벨만 바깥 공간을 요구하는 것을 확인했다. 제목은 프레임
안쪽 위에서 시작하므로 제목 크기에 비례한 절대 아래끝 앵커로 모든 크기를 맞추지 않는다.

구현 연결은 `CartesianLayout의 글줄/축 계획 → 숫자·범주·범례의 공간 예약 → 최종 plot과
동일 ValueScale → bar/line/stock/combo의 그리기`로 묶는다. 축 범위를 paint에서 다시 정하거나
음수 막대 높이를 0으로 숨기는 경로를 제거한다. 기존 3D 투영·percent 및 저장 명시 범위는
같은 최종 계획 안에서 구별하고 실제 소비까지 확인한다. 새로운 회귀/golden은 두 backend의
시각 선행 조건을 마친 뒤 추가하며 이 분석만으로 통과를 선언하지 않는다.

## 공통 계획 Native060의 중간 검증

Native060은 `311a342dab` 위의 변경 소스를 177개 파일 SHA로 고정한 dirty 빌드다.
`char-overlap-native-build-060-result.json`과 `source-snapshots/native060/`에 생산 소스를

컴파일은 경고가 없었다. 이 상태의 fresh WASM은 아직 빌드하지 않았다.

동일 원본·독립 Print·글꼴의 101조건을 보정 전 Native059와 비교했다. 모두 한 쪽이며
