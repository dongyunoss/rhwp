### Native209의 실제 실행 결과와 아직 남은 수식 증거

`fb759a980d50268b29274f94ccaee406a7e975fd`의 Native209는 공용 target·빌드 잡 8개로

동일한 실행에서 확인했다. 전체 nextest나 fresh WASM 완료로 확장해 보고하지 않는다.

3290의 같은 원본·독립 Print를 base194와 Native209에서 전쪽 대조했다.
원본·inline-unbound·duplicate-field-owner 각 16쪽, 후보 48쪽 모두 90% 이상이다.

99.62967%, 99.62718%다. 3293의 inline-unbound 1쪽 review·standalone overlay에서
`Before: 1 / 1`과 본문·꼬리말의 소속을 직접 확인했다. 작은 raster 농도 잔차는 남는다.
기존 독립 ±2px 번호 원점 검사도 3286에 포함됐다. fresh056과 전쪽 대조는 아직 진행 전이다.

다른 수식 실패의 원인을 확정하려고 기존 테스트의 private helper를 그대로 사용해 여섯
모델을 HWPX로 저장했다(3289). 저장 전·재열기 후 EquationNode의 layout_box는 여섯 개 모두
바이트상 같은 JSON이었다. 생성기로 임의의 다른 정상 입력을 대신하지 않았다.
3291에서 여섯 파일을 모두 한컴 2020 11.0.0.9136, PrintMethod0, 전처리 없이 각 한 쪽으로
출력했다. 원본·요청·job·전체 상태·PDF SHA를 output에 보존했다.

3292의 실제 PDF에서 구형 `%`·`△`·`․`는 Type3 프로그램이고 현대 `%`는 HyhwpEQ의
U+E042다. 구형 COLOR는 수식 본체가 표시되지 않는다. 이는 기존 테스트가 가정한
구형 PUA/현대 비-PUA 및 구형 COLOR 투명성의 근거를 재검토할 자료다.
PDF에는 HCRBatang U+FFFC도 추출된다. 이 추출만으로 가시 잉크나 잘못된 fixture라고
판정하지 않는다. 실제 원문 자리표 소유·직렬화와 원점을 함께 추적해야 한다.
3295의 Native209 전쪽 비교에서 이 여섯 합성 입력은 미달이다. 따라서 이 단계에서는
그 수식 검사·기대값·golden을 변경하지 않았고, 새 렌더링 회귀의 완료 입력으로 추가하지 않았다.
49조건·1,772쪽 및 #265 대조군 통과와 별도로 원인 보정을 계속한다.

fresh056은 같은 fb759a980d의 정확한 Git archive에서 표준 release·locked wrapper·실제
wasm-opt 경로로 실행을 시작했다(3294·3296). Cargo 잡 8개와 같은 절대 target을 재사용한다.
Native209와 외부 Rust 검사 종료를 확인한 뒤 시작했으며, 완료·최적화·패키지 해시와 실제
후속 시각 출력 확인 전에는 fresh 결과를 통과로 기록하지 않는다.

### #8038 강조점 helper 정정과 표 여백의 공통 원인

#8038 원 head `20a7d2787ae531036ceceb88818504e87093cb7c`의 본문·현재 공개 원문을
읽고 누적 `5370948158ce` 및 후속 장식 기하 보정과 대조했다. 새 PR을 체리픽하지 않았다.
원 테스트의 U+25CF 문자열 가정과 현재 출력 U+0307·transform이 달랐다. 같은 `fixture`로
출력한 한컴 2020 Print에 Native209/fresh056은 한 쪽 모두 raw100%였으며, 3323에서
review·standalone overlay를 양쪽 직접 확인했다.

검사 helper가 결합점의 실제 transform을 적용한 보수적 em 상자 상단을 읽도록 정정했다.
clip 포함과 캐럿 불변, 위 밑줄 0·6·10의 획 포함·clip 하단 보존을 유지한다. 3324에서
옛 helper는 강조점을 찾지 못해 FAIL, 같은 runtime의 3325에서 두 장식 검사는 PASS였다.
[입력·독립 Print·전체 TSV·대표 이미지](../pr/assets/raised_dot_clip_20261025/README.md)를 보존했다.
이 실행에서 계산 빈 호스트의 기존 관계·독립 좌표 다섯 검사도 PASS였고 표 여백 검사는 FAIL이었다.

표 원 검사의 source `e1193c21c592180a5b2b4b001b43a8dc457b9c70`와 누적 `a971548d1e02`는
문단 기준 표의 바깥 상자 끝 아래에 뒤 빈 줄·본문이 놓여야 한다는 관계를 요구한다.
관련 #7559 원문과 #7265/#7430/#7538의 저장·편집 원점 계약도 대조했다. 허용치를 늘리거나
#4068의 정확한 괘선 원점을 되돌리는 방식으로 통과시키지 않는다.

3324의 실제 API 입력은 구현 태그 줄(`0x80060000`)을 가진 계산 빈 호스트다.
여백 0일 때 표 132.3~166.5px, 뒤 본문 166.5px지만 5,000HU 때 표 198.9~233.1px,
뒤 본문 153.6px였다. 저장 HWPX도 동일했고 독립 Print에서는 본문이 아래 여백 뒤에 놓인다.
3323의 같은 페이지 review·overlay에서 표 위로 역전된 두 문단을 직접 확인했다.
HWP 저장은 현재 별도 283HU 기본 여백 계약이므로 원본 5,000HU를 보존한 것처럼 보고하지 않는다.

공통 원인은 `computed_host_frame::resolve`의 측정·배치 결과 자체가 아니라 그 소비다.
생산: `table_top`은 괘선 원점, `occupied_bottom`은 아래 여백까지다. 실제 소비:
`typeset.rs::place_table_with_text`가 이 `table_top`을 배제 시작점으로 사용해서 괘선 위의
바깥 여백을 빈 공간으로 만들었다. `state/computed_float_line.rs`의 첫 줄 조회는 그 틈에
들어가는 후속 줄을 그대로 두고, 최종 `layout.rs`는 `float_pushed_line_spacings.origin`을
그대로 받아 위에 본문을 그렸다. 별도 paint 이동이나 마지막 clamp가 원인이 아니다.

같은 생산 결과의 `ComputedEmptyHost`에 `outer_box_top`을 추가해 괘선 원점에서 원본 위
여백을 제외한 바깥 상자의 시작점을 발행한다. 배제 영역이 이 값을 소비하고, 첫 줄의
fit·실제 paint 원점은 기존 공유 결과를 계속 사용한다. 양수 오프셋이 만드는 실제 틈과
바깥 여백의 점유를 구분하며, 호스트 빈 줄의 독립 advance·표 원점·수용 하단은 유지한다.
저장된 실제 줄·투영 줄·RowBreak·분할·절대 배치는 이 계산 빈 호스트 생산 경로가 아니므로
기존 소유자가 유지된다. 문서명·여백 크기 임계값·버전별 보정은 추가하지 않는다.

다음 동결 Native/fresh에서 원 여백 검사와 14입력의 작은/큰 빈 줄·양수 오프셋 위 틈·
줄 겹침·다음 문단 앞 간격 대조를 함께 실행한다. 여백 0/5,000HU 네 입력의 독립 Print
전쪽 대조와 대표 판독도 필요하다. 현재는 원인에 근거한 구현을 동결하는 단계이며,
이 새 표 여백 runtime의 빌드·수정 후 회귀·시각 통과는 아직 주장하지 않는다.
