# 인라인 개체 앞뒤의 원문 주소와 논리 캐럿 주소

## 범위와 현재 증거

현재 `review/semanticist21-20261019`의 45개 PR 범위를 유지하며 새로운 PR은
체리픽하지 않는다. 행정업무운영 편람의 추가 보정은 사용자가 제외했다.
당시 53개 integration 실패 중 필드 6개·자동 번호 소속 1개와 겹침 선택 영역을
공통 주소 소비 경로에서 먼저 분석한다. 다른 실패를 완료로 분류하지 않는다.

원 PR #7671의 `67764a121`은 HWP의 자동 번호 자리표 저장을 고쳤다.
통합 #7935의 `ed97e78cb1`은 원문 scalar 주소에 표시값을 저장하고 실제 쪽
소속으로 값을 확정했다. 그 뒤 현재 브랜치는 인라인 개체를 편집 한 칸으로
세도록 TextRun.char_start를 논리 주소로 발행한다. 두 주소를 같다고 보던 소비자가
남았는지 확인한다. 원문은 UTF-16 저장 위치·Unicode scalar이고 공개 캐럿은
인라인 개체도 한 칸이다. 위첨자·그림의 화면 폭으로 주소를 추측하지 않는다.

`field-source-axis-wasm042-1750.json`과 고정 devel 대조 1751에서 같은 6개
HWP/HWPX의 필드 런 시작이 1→2, 뒤 글자가 2→3으로 바뀌는 것을 실제 공개
getPageTextLayout로 관측했다. 해당 6개 원인 경로 소스는 fresh042와 현재 제품이
바이트 동일함을 기록했다. 이 진단을 새 fresh043 출력으로 표시하지 않는다.

더 긴 반례는 원본 pr7671-endnote.hwpx를 공개 insertText로 편집해 같은 문단
번호 앞에 40/90개의 명시 줄바꿈을 넣었다. 고정 devel은 2/3쪽을 출력하지만
후보는 부분 문단에서 원문 201/451 위치의 필드 소유를 찾지 못하고 모든 쪽의
getPageTextLayout에 실제 렌더링 오류를 반환했다. 1752는 실행·저장 입력을
보존하며, 단순 원점 핀 변경으로 해결할 수 없는 현재 회귀다.

두 편집 저장본의 제품 메타데이터는 원본과 같은 한컴 2020 11.0.0.3524다.
MCP에 engine 2020·target pdf를 명시하고 start/status/download로 인쇄했다.
실제 11.0.0.9136·PrintMethod 0·hancom2020_pdf_driver_one_up을 확인했다.
원본·PDF·실행 영수증은 ignored output의 mcp-partial-field-axis-1753에 있다.
독립 Print 쪽수와 마지막 번호는 partial-field-axis-print-observations-1754.json에
연결한다. 새 회귀 추가는 관련 전쪽 Native/fresh 90%와 직접 판독 뒤에 한다.

## 구현 전 소비 경로와 보정 계획

자동 번호 자리표 해석에서 원문 위치와 공개 모델의 논리 위치를 함께 발행한다.
기존 측정·표시 문자열은 원문 위치를 계속 읽고, 부분 문단의 TextRun 소유 판정은
같은 결과의 논리 위치를 읽는다. 최종 layout_field_values의 원문 키와 저장 텍스트는
유지한다. 뒤에서 좌표를 clamp하거나 FullParagraph로 분류해 오류를 숨기지 않는다.

기존 6개 Print 검사는 원문 제어 위치 확인을 유지하며 논리 TextRun 소속과 연결한다.
정확한 독립 PDF 좌표·허용 오차는 유지한다. 겹침·주석의 커서/선택은 같은 주소가
그리는 실제 경계를 소비하는지 별도로 확인한다. 현재 빌드 중인 fresh043 소스를
바꾸지 않았다. 빌드 종료 후 근거가 확보된 수정들을 함께 적용·검증했다.

## 원문 주소와 논리 소유 보정의 실제 결과

`auto_number_positions.rs`가 원문 자리표와 논리 칸 주소를 함께 발행한다.
`body_page_fields.rs`의 부분 문단 소유 조회는 논리 칸을 읽고 표시값 저장 키는
원문 주소를 유지한다. TextRun의 겹침 한 칸 계산도 커서와 필드 조회가 공유한다.
기존 여섯 Print 검사의 원문 제어 주소와 독립 기대 좌표는 유지하고, 런 소속만
공개 logical_control_positions 계약으로 확인하도록 수정했다.

Native116에서는 두 반례의 렌더링 오류가 사라졌고 Print 쪽수 2/3쪽과 같았다.
40회 입력은 97.05948%/96.57933%, 90회 입력은 100%/100%/89.59755%다.
1765 전쪽 TSV와 1767의 새 review·overlay를 직접 읽었으며, 마지막 쪽 미달을
해결 전 완료로 분류하지 않았다. 현재 실패 재실행 1766은 35개 통과·46개 실패다.
전체 Rust 검증 결과가 아니며, 필드와 자동 번호 대조 및 첫 혼합 조각의 새 검사
두 개는 실제 통과했다.

## 저장 줄의 미주 슬롯과 표시 경계

1768에서 원문과 구성 줄을 함께 읽었다. 90회 입력의 미주 제어는 UTF-16
451에서 시작하고 마지막 저장 줄은 459에서 시작한다. 앞줄의 텍스트는 446부터
449까지이며 개행은 450이다. 제어 뒤 자동 번호 자리표의 scalar 주소 451을
미주 제어의 줄 소속으로 쓰면 미주가 다음 줄로 밀린다. 독립 Print는 미주를
앞줄 오른쪽에 놓고, 해당 줄의 `연결검사` 네 글자와 미주 사이도 배분한다.
PDF의 네 글자 원점은 약 104.58pt 간격이며 임의 px 보정의 근거가 아니다.

`NoteLineSlots`는 저장 줄의 수·원문 경계·높이·폭이 현재 구성과 일치할 때
기존 control_slot_line_index의 원시 슬롯 소속을 읽는다. 새로 분할한 줄이나
서로 다른 출처의 사다리를 수용하는 조건은 완화하지 않는다. 표시 경계는
소유 줄의 원문 텍스트 끝이고 원문·논리 주소는 바꾸지 않는다.
같은 결과를 폭 측정, 실제 주석 방출, 이어지는 조각의 논리 칸 집계가 소비한다.
개행 뒤 제어를 같은 물리 줄이 소유할 때만 강제 줄 끝의 배분 억제를 해제하며,
말미 미주 한 칸을 간격 배분에도 포함한다. 원문 개행의 논리 한 칸은 유지한다.

Native117에서 두 입력의 전쪽·대표 PNG와 기존 필드/미주/겹침 정상 대조를
먼저 확인한다. 새 반례의 정식 fixture·회귀 추가는 양쪽 전쪽 90% 이상과 직접
판독 뒤에만 진행한다. 행정업무편람의 추가 개선은 수행하지 않는다.

## Native117 선행 검증

공용 target·빌드 잡 8개로 Native117을 242.68초에 빌드했고 실제 exit 0을
확인했다. 1769의 두 원본 5쪽과 1781의 대조군 두 개 6쪽은 raw 실루엣이
모두 100%이며 독립 Print 쪽수도 2/3/3/3쪽과 일치한다. 대조군은 같은 공개
insertText의 삽입 위치를 미주 뒤로 옮겨 미주는 앞쪽, 쪽번호는 뒤쪽 조각에
남긴 입력과 각주 뒤 번호 앞에 명시 개행을 넣은 입력이다. 입력 생성 단계에서
저장 LineSeg를 수동으로 고치지 않았다.

1784에 새 Native117의 review와 standalone overlay 다섯 쌍을 만들었다.
90회 입력 3쪽에서 미주 번호가 앞줄 오른쪽에 있고 다음 줄은 `3뒤`로 시작한다.
본문 네 글자·미주 사이 배분과 구분선/주석 본문을 독립 Print에 직접 대조했다.
100%는 2px raw 실루엣 값이며 색상·안티앨리어싱까지 같은 픽셀이라는 뜻은 아니다.

고정 base Native1504(2e087 기준)의 같은 입력·같은 Print 대조 1777에서도
90회 입력 3쪽은 89.59755%다. 이 배치 차이는 이번 주소 보정이 만든 후퇴가
아니지만 새 반례의 정상 회귀 선행 조건을 충족하도록 보정했다. 최신 f7abae의
동일 실행 결과로 표시하지 않는다.

기존 집중 검사 1776은 행정업무편람 전용 7개를 제외한 98개가 모두 통과했다.
과거 실패와 기존 필드 정상 대조를 재실행한 1770은 35개 통과·46개 실패이며
Native116과 결과 집합이 같다. 전체 Rust 검증 완료나 남은 실패 해결을 뜻하지
않는다. 이 단계는 소스와 기존 검사 계약 보정의 중간 커밋이며, fresh044·새
정식 회귀·최종 전체 검증과 PR 제출은 아직 완료하지 않았다.
